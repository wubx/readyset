# M2-A：Stream 增量同步、UPDATE / DELETE 与重复投递

后续进展：[声明式 Databend HTTP 入口及后台自动同步](GATEWAY.md)。本文保留 M2-A 阶段的实验边界。

## 范围与结论

本阶段跑通真实链路，而不是模拟 CDC 消息或只更新 Python 字典：

```text
Databend Standard Stream
  → 源端事务：消费 Stream + 写不可变 outbox + 写 batch_meta
  → 从另一个客户端重新读取已提交批次
  → 单消费者、严格串行应用 ReadySet
  → 同一底表写批次包含行变更和 Databend generation / sequence checkpoint
  → 等待明确的底表持久化状态
  → loopback ReaderHandle RPC 全表结果对比
```

两轮独立数据库实验，初始分别 **2,000 / 1,000 行**，每轮 **142/142 条断言通过**。
每轮消费 6 个已提交批次、应用 1,517 条行变更，另有 13 次重复或旧批次投递均跳过。
最后源表与 ReadySet 查询结果分别为 **1,939 / 939 条现存记录**，checkpoint 都是 6。

这验证了增量链路的基本正确性，尤其是 **旧批次不覆盖新版本、不复活已删除记录**。
**这不是完整的 M2 可靠复制器，不代表进程/节点崩溃恢复已经实现，更不代表端到端 exactly-once 或生产 SLA。**
尚未实现常驻自动轮询、恢复 bootstrap、源端消费 fencing、outbox GC 和 SQL wire frontend。

## 实现

### 1. 固定初始边界

在新建 POC 表装入合成数据后创建 Standard Stream，然后分页扫描：

```sql
SELECT id, payload, score, note
FROM <new_database>.source_rows
AT (STREAM => <new_database>.source_stream)
WHERE id > <last_key>
ORDER BY id LIMIT 500;
```

首个分页没有 `WHERE`。扫描不消费 Stream。ReadySet 初始全表加载完成后才设置 sequence 0，
注册 `WHERE id = ?` 的全量 reader。没有业务应用按 key 填缓存，也没有点查回源路径。
增量中首次出现的新 key 也在后续全表对比中读取并核对。

POC 每次创建新数据库，以该数据库名作为 generation；不是把原生 Databend snapshot ID
假装成递增 LSN。生产实现需要为重建 Stream、重建源表及重新 bootstrap 显式生成新 generation。

### 2. 源端原子捕获

源端表：

- `source_rows(id, payload, score, note)`：固定列，合成唯一 BIGINT key。
- `source_stream`：Standard Stream，`APPEND_ONLY = false`。
- `outbox(batch_id, id, payload, score, note, action, row_id, is_update)`。
- `batch_meta(generation, batch_id, row_count, changes_sha256)`。

每次只有一个捕获者，且不复用已经提交的 batch_id：

```sql
BEGIN;
INSERT INTO <db>.outbox
SELECT <batch_id>, id, payload, score, note,
       change$action, change$row_id, change$is_update
FROM <db>.source_stream;
-- 在同一事务读取完整 outbox，核对 count 并计算 changes_sha256
INSERT INTO <db>.batch_meta VALUES (<generation>, <batch_id>, <count>, <sha256>);
COMMIT;
```

`sequence` 是当前 Databend 的保留字，所以源端列名使用 `batch_id`；Rust/JSON 中仍称 sequence。
本阶段显式回滚首批捕获一次，验证 Stream 内容不变，outbox 和 metadata 均没有遗留记录，
然后用同一 batch_id 正常捕获。正式投递前通过 observer 客户端重新读取已提交 outbox 和 metadata，
验证条数、generation、batch_id、SHA-256，不能仅信任提交前的 Python 缓冲。

复用 M0 的有界、session-aware HTTP 客户端。SQL 失败或网络结果不确定都不自动重发 SQL；
保留最早的错误，失败事务不会继续尝试 COMMIT。回滚也失败时，将清理错误附加到原始异常。

**边界：** 事务前的“batch_id 不存在”检查不是并发唯一性保障。这里只允许一个串行捕获者；
多捕获者的租约、fencing、提交冲突后重新判定进度及 uncertain-commit resolution 仍未实现。

### 3. 真实的 Databend checkpoint 类型

`replication-offset/src/databend.rs` 新增 `DatabendPosition { generation, sequence }`，
并在 `ReplicationOffset` 末尾追加 `Databend` 变体：

- 只允许同一 generation 的序号比较；跨 generation 返回不可比较/错误。
- 文本格式：`databend:<generation>:<sequence>`。
- JSON 和 bincode roundtrip 测试；旧三个变体的 bincode discriminant 不变。
- 既有 PersistentMeta golden serialization / deserialization 测试仍通过，未重写旧格式。
- `dialect()` 为本 POC 规范化本地表返回 MySQL，**不表示支持 Databend SQL 方言**。

追加变体使旧 offset 数据仍可读取，但旧 binary 不认识新的 Databend 位点；
这不是混合版本或降级兼容承诺。所有实验只使用新 POC 状态目录。

### 4. 批次应用与去重

`readyset-databend/src/lib.rs` 提供类型化批次与 `Sink`。每次应用前读取引擎底表的 checkpoint，
不把同步进程内的计数器或旁路 JSON 文件当作可靠位点：

| 条件 | 行为 |
| --- | --- |
| generation 不匹配 | 拒绝 |
| row_count、SHA-256、操作类型或唯一 key 前提不满足 | 拒绝，包括已经过时的批次 |
| sequence ≤ 当前 checkpoint | 校验后跳过，**不发任何行操作到 dataflow** |
| sequence = 当前 checkpoint + 1 | 应用 |
| sequence 更大、存在缺口 | 拒绝，不乱序覆盖 |

Stream 是两个边界之间的净变化，不是有序 WAL。保留 `change$row_id` 和 `change$is_update`
作为证据，但不以其推导全局事件顺序。应用时先撤回所有 DELETE before-image，再插入所有 INSERT
新行，避免一边插入一边删除时破坏更新、key 移动或已删除 key 重用。
每批限制为最多 10,000 条操作，只有一个 Table RPC，不拆成多个独立提交。
在该单表/无分片 POC 中，生成的记录与 `SetReplicationOffset` 走同一 RocksDB WriteBatch。

去重必须发生在调用 `Table::perform_all` **之前**，不能只依赖持久化层的旧位点过滤：
底表生成/转发 dataflow 记录在持久化步骤之外，存储忽略旧写入不等于 reader 一定免受重复记录影响。
`Sink::apply` 使用可变借用，实验进程中任一时刻只有一个批次在途；这不是跨进程的排他所有权协议。
RPC 或持久化等待结果不确定时，实验进程立即失败，不盲目继续应用后续批次。

数据和 checkpoint 的本地存储批次并不与 Databend COMMIT 构成跨系统事务。源端保留所有批次，
后续恢复设计需要在重新获得正确的引擎状态后，重读 outbox 并依据 checkpoint 决定重放。

### 5. 持久化确认与 reader 校验的重要区别

本轮发现两个不能忽略的 API 语义：

1. **`PersistencePoint::UpTo(target)` 不是 batch target 已完整落盘的证明。**
   该值标记未持久化工作的起始低水位。本 POC 不接受该值作为批次成功条件，
   而是等到 checkpoint 达标且单表系统返回 `PersistencePoint::Persisted`。
   当前 `wal_flush_interval_seconds = 0` 的同步写路径会设置 RocksDB sync，
   但 offset 更新后共享 WAL 状态可停留在 `Unflushed`，又没有后台 flush 线程更新状态。
   M2 因此配置 1 秒后台 WAL flush，并等待明确的持久化状态；没有修改这个既有核心逻辑。
   这也使本实验的批次耗时不能直接作为生产同步延迟数据。
2. **`ReaderHandle::len()` 不能作为删除后的现存行数。**
   reader map 可保留已删除 key 的空槽。2,000 行实验首批后实际现存 1,970 行、key slots 为 2,020；
   最终实际现存 1,939 行、key slots 为 2,021。验证器逐条比较所有源表现存行、检查所有已知删除
   key 返回空，再枚举 reader key 检查额外 key 不含多余现存记录，而不是错误地要求 `len == count(*)`。

批次 ack 只确认底表 checkpoint 和持久化条件，不承诺此刻 reader 已全部追平。
实验随后通过有界等待核对 reader 内容；没有测量持续写入负载下的 reader lag。

## 实测覆盖

每轮已提交的批次如下；UPDATE 通常对应一条 DELETE 和一条 INSERT：

| 批次 | DELETE | INSERT | 合计 | 场景 |
| --- | ---: | ---: | ---: | --- |
| 1 | 250 | 220 | 470 | 更新 200 行、纯删除 50 行、插入 20 个全新 key；先回滚一次再正式捕获 |
| 2 | 131 | 102 | 233 | 更新到更新版本、删除前批更新/插入过的行、key 移动、删除后重插 |
| 3 | 4 | 2 | 6 | 再删除、NULL/空串变化、Int64 最小值、更新移动后的 key |
| 4 | 0 | 0 | 0 | 空批次也提交 metadata 并推进 checkpoint，重复投递仍安全 |
| 5 | 3 | 3 | 6 | 同一捕获区间多次 UPDATE、DELETE 后 INSERT、重用历史删除 key |
| 6 | 401 | 401 | 802 | 较大批量 UPDATE，仍为单 RPC |

每轮另外验证：

- 批次 1 连续投递三次。
- 批次 2 之后重放批次 1：不能用 v1 覆盖 v2，不能复活已经删除的记录。
- 重建 sink、创建新 mutator 和 raw controller client，从引擎读取 checkpoint 2，再重复投递批次 2。
- 批次 3 删除先前重插的行后，再重放旧插入批次：不能复活。
- 全部应用后，**从源端 outbox 重新读取**批次，按 `5, 3, 2, 1, 6, 4` 顺序重复投递。
- 缺号、错误 generation、截断批次、篡改内容四类输入在修改前拒绝，checkpoint 和查询内容不变。

两轮各 13 次全表状态对比，包含初始与多种重放后的状态。比较所有返回列，而不只是 count 或 payload。
合计比较 **37,672 条现存行、1,854 次不存在 key**，另检查 1,828 次额外空 key 槽位；
两轮分别执行 175 / 145 条 SQL，共 320 条。

最终独立数据库：

- `readyset_m2_20261112_084229_09402b5b`：2,000 → 1,939 行。
- `readyset_m2_20261112_084247_f3ef221b`：1,000 → 939 行。

单元测试另覆盖 UTF-8 / Int64 / NULL 的跨语言 checksum 一致性，以及 RocksDB 受控关闭/重开后
行数据和 Databend checkpoint 的一致性。**受控重开不等于进程被杀、节点掉电或分布式恢复测试。**

## 复现

只能在开发分支执行；所有改动保持未提交：

```bash
git branch --show-current  # poc/databend-stream-m0

export LIBCLANG_PATH=/tmp/readyset-m1-libclang
# 若不存在，按 M1.md 创建 libclang.so 到 /usr/lib/llvm-18/lib/libclang.so.1 的临时软链接
cargo build --locked -p readyset-databend --bin databend-m2 -j 8
cargo test --locked -p readyset-databend -p replication-offset -j 8
cargo test --locked -p dataflow-state --lib replication_offset_databend_rows_and_checkpoint_reopen -j 8
cargo test --locked -p dataflow-state --lib meta_ -j 8
cargo clippy --locked -p readyset-databend -p replication-offset --all-targets --no-deps -- -D warnings
python3 -B -m unittest discover -s readyset-databend/poc -p 'test_*.py' -v

# 会新建独立数据库；不修改既有业务对象。密码从私有 DATABEND_PASSWORD 环境读取，空值可用。
python3 -B readyset-databend/poc/m2.py \
  --endpoint http://192.168.1.100:8000 --user root --rows 2000 --confirm-create
python3 -B readyset-databend/poc/m2.py \
  --endpoint http://192.168.1.100:8000 --user root --rows 1000 --confirm-create
```

Rust runner 与 Python 捕获器通过本地 stdin/stdout JSON-lines 编排，这是实验控制接口，不是公开服务协议。
查询通过真实 loopback TCP ReaderHandle RPC 访问嵌入式 ReadySet；没有 SQL frontend 或 Databend fallback。
只关闭本轮自己启动的子进程，不重启外部服务。所有新建源端 POC 表、Stream 和本地证据保留，不自动 DROP。
