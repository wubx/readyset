# M1：静态全表加载与随机 key 点查

## 本轮结果

2026-11-12，在分支 `poc/databend-stream-m0` 完成两轮独立 ReadySet 实例验证，随机种子分别为 42、2026。
两轮均加载 **100,000 行**，随后随机遍历全部 key，并逐行比较全部返回列，结果全部正确。

每轮还验证：10,000 次重复均匀随机查询、1,000 个不同的不存在 key、16 并发下 10,000 次随机查询。
每轮共 121,000 次点查，两轮共 **242,000 次**，所有返回结果与源端固定快照一致。
查询阶段不持有 Databend 客户端，不存在源端 fallback。

这证明“全表覆盖、任意 key 首次查询、空结果本地返回”的基本链路成立，不是只测热点缓存。
**尚未接入 SQL wire frontend、跨机网络或持续增量，因此不是最终生产 SLA。**

## 架构与改动

```text
Databend（用户指定的测试实例）
  → 新建独立合成数据表 / Standard Stream
  → 固定 snapshot ID
  → Python 按 key 分页导出 JSONL
  → Rust 读取并检查唯一键
  → ReadySet Table::insert_many 批量加载
  → 注册参数化点查 / full replay
  → 确认 reader 完整行数及非 partial
  → 随机遍历全表校验 / 负查询 / 并发测试
```

新增 crate `readyset-databend` 和 binary `databend-m1`；根 `Cargo.toml` 注册 workspace member，
`Cargo.lock` 仅增加该 crate 的依赖列表。没有修改已有 ReadySet 查询/存储核心。

- `src/bin/m1.rs`：真正调用本工程的 ReadySet server、Table 和 ReaderHandle API。
- `poc/m1_export.py`：复用 M0 的有界 HTTP 客户端，固定快照导出和源端参考点查。
- `poc/test_m1_export.py`：Int64 精度、NULL/空字符串、输入校验及统计测试。

源端导出和 ReadySet 执行刻意分开：用于隔离变量，确认全部查询由索引副本完成。
这不是生产增量连接器；未来由同步组件持续维护副本，而不是应用填充热点 key。

## 数据与环境

- Databend：`http://192.168.1.100:8000`，`root`，`v1.2.962-652b12b49c`。
- 数据库：`readyset_m1_20261112_080821_c27444c7`，只含本次合成数据。
- 固定快照：`01a1ceccf80773c4924dd432fbedbf92`。
- 表：`source_rows`；Stream：`initial_boundary`，M1 不消费。
- Key：`id = number * 17 + 7`，非稠密 BIGINT。
- 其他列：UTF-8 payload、带 Int64 最大/最小值的 score、包含 NULL / 空串 / UTF-8 的 note。
- JSONL：14,438,097 字节；SHA-256：
  `0bcec4cff169a91a20a97272b4fc93e71e9de643e87eb30ad6f3445ecb5e93b3`。
- Host：Linux x86_64，AMD Ryzen 9 5950X，16 cores / 32 threads；主机存在其他负载，未隔离 CPU。
- Rust：1.99.0；本轮为 **dev / unoptimized + debuginfo**，不是 release benchmark。
- Tokio：8 worker threads。
- ReadySet：server 与压测客户端同进程，ReaderHandle 经 loopback TCP RPC 读取。
- 底表持久化使用 RocksDB，`DurabilityMode::Permanent`；完整 reader 保存在内存，不启用实验性 full-materialization 落盘。

## 加载与就绪

1. 用 Standard Stream 在源表初始化之前开启 change tracking。
2. 生成 100,000 行数据并取得固定 snapshot ID。
3. 所有导出页使用 `AT (SNAPSHOT => ...)`，每页最多 1,000 行，按 `id` keyset 分页。
4. 导出时检查 key 严格递增、行数和 Int64 范围，不经过浮点转换。
5. Rust 再检查重复 key，按 1,000 行一批写入 ReadySet。
6. 注册：

   ```sql
   CREATE CACHE m1_by_id FROM
   SELECT id, payload, score, note
   FROM m1_source
   WHERE id = ?;
   ```

7. 通过 `Builder::disable_partial()` 使用全量物化。
8. 首次 lookup 前，检查 `reader.len() == 100000`，同时查询 `materialization_info()`，
   确认底表和 reader 都 `partial = false`。
9. 之后才开始计时和结果验证；没有先用点查逐 key 预热。

两轮 ReadySet batch submission 分别为 **15.00 / 15.06 秒**，
注册查询及等待完整 reader 为 **1.17 / 1.19 秒**。
源端导出约 **4.23 秒**，不包含生成测试表和基线查询的耗时。
这些是阶段计时，不是有恢复协议的生产快照吞吐保证。

### 注意：不能把 replication_enabled=false 当作通用外部装载模式

当前分支中，该开关表示 shallow-only，leader election 会清除 deep state 和持久化表。
M1 因此保留默认 replicator 配置，但不设置任何 upstream / CDC URL；已有逻辑不会启动内建复制任务。
不应为了“禁用 MySQL 复制”误用 shallow-only 开关。

## 点查结果

单位：延迟为毫秒，QPS 为每秒完成查询数。

| 场景 | 次数/轮 | seed 42 P50 / P95 / P99 | seed 2026 P50 / P95 / P99 | QPS（42 / 2026） |
| --- | ---: | --- | --- | --- |
| 全表随机排列，所有 key 首次查 | 100,000 | 0.235 / 0.268 / **0.290** | 0.236 / 0.273 / **0.295** | 3,107 / 3,096 |
| 重复均匀随机 key，串行 | 10,000 | 0.234 / 0.261 / **0.286** | 0.238 / 0.272 / **0.294** | 3,136 / 3,071 |
| 不存在的 key，串行 | 1,000 | 0.210 / 0.238 / **0.260** | 0.211 / 0.232 / **0.263** | 4,640 / 4,647 |
| 均匀随机 key，16 并发 | 10,000 | 0.574 / 0.831 / **0.938** | 0.574 / 0.837 / **0.950** | 23,222 / 23,412 |

整个实例的第一条 lookup 分别为 **0.441 / 0.462 ms**。
全表首次遍历的最大延迟分别为 **2.163 / 3.512 ms**，因此不能将 P99 误解为所有请求都小于 1 ms。

### 测量解释

- “首次查”指该 key 在这个新建 reader 中从未被 lookup；不是整个进程或 OS page cache 冷启动。
  全量物化本来就会提前准备全表状态。
- 单次延迟覆盖 lookup 调用、loopback RPC、解码和结果物化，不含预期行构造/比较。
- QPS 使用压测阶段总时间，包含结果正确性比较和调度；不是开放环饱和压测。
- 首次全表遍历还保存原始延迟数组，因此其 wall time 包含一次文件写出。
- 并发阶段用独立 reader handles，没有用一个互斥锁将客户端请求串行化。
- 本轮无 SQL parsing / MySQL wire 序列化，也没有远程应用网络。
- 两个随机种子是可重复性检查，不是统计显著性的长期 soak test。

Databend 同一固定快照的 100 次随机点查参考值：P50 **19.00 ms**，P95 **22.34 ms**，P99 **23.67 ms**。
该路径包括 Python HTTP、远程网络、query lifecycle 和本地日志，与本地 ReaderHandle RPC 不等价，
**不得据此宣称端到端加速倍数**。

## 状态容量观察

seed 42 的 materialization introspection：

- 底表：约 23.63 MiB（估计 100,000 行，含索引）；
- reader：约 19.54 MiB（精确 100,000 key）；
- 两者都显示非 partial，点查索引列为 `id`。

整个 Rust 实验进程 RSS 约 **232 / 236 MiB**。它同时包含 ReadySet、导入数据/校验 oracle、
客户端和分配器开销，不能直接当作生产 ReadySet 单独部署所需内存。
状态统计是引擎估算，也不能直接作为容量线性外推依据。

## 复现

### 1. 构建与测试

使用仓库 `rust-toolchain.toml` 的 1.99.0 工具链。需要 clang/libclang 与 RocksDB 构建环境。
本机只有版本化的 libclang 文件，使用临时软链接，不更改系统环境：

```bash
mkdir -p /tmp/readyset-m1-libclang
ln -sfn /usr/lib/llvm-18/lib/libclang.so.1 /tmp/readyset-m1-libclang/libclang.so

LIBCLANG_PATH=/tmp/readyset-m1-libclang \
  cargo build --locked -p readyset-databend --bin databend-m1 -j 8

LIBCLANG_PATH=/tmp/readyset-m1-libclang \
  cargo test --locked -p readyset-databend --bin databend-m1 -j 8

python3 -B -m unittest discover -s readyset-databend/poc -p 'test_*.py' -v
```

本轮 Rust 单元测试 **4/4**，Python 测试 **9/9**（含 M0 的 5 项）。
`cargo clippy --locked -p readyset-databend --bin databend-m1 --no-deps -- -D warnings` 也已通过。

### 2. 生成并导出独立源表

以下会在明确指定的 Databend 实例创建新 POC 数据库，不修改已有业务对象：

```bash
python3 -B readyset-databend/poc/m1_export.py \
  --endpoint http://192.168.1.100:8000 --user root \
  --rows 100000 --baseline-queries 100 --confirm-create
```

密码仍从 `DATABEND_PASSWORD` 私有环境读取，不放入命令参数或日志。
命令打印本次导出目录。每次使用新数据库，因此不会覆盖现有测试或业务数据。

### 3. 装载并点查

```bash
target/debug/databend-m1 \
  --input /tmp/readyset-databend-m1/<export-database>/rows.jsonl \
  --output /tmp/readyset-databend-m1/<new-engine-run-directory> \
  --seed 42 --batch-size 1000 \
  --repeat-queries 10000 --missing-queries 1000 --concurrency 16
```

输出目录必须不存在；Rust binary 会启动并在结束时关闭独立本地 ReadySet。
报告是 `report.json`，首次全表点查原始延迟是 `first_touch_us.json`，
完整 reader 的初始状态在 `materializations.json`。查询结果不正确、未完整就绪或超时都会退出失败。

这只是实验 runner：未提供长期 SQL 服务，也没有基于本次 LocalAuthority 重启恢复的命令。
`Permanent` 底表文件保留不等于已经实现可恢复副本协议。

## 证据位置

仓库中保存 `poc/evidence/m1_20261112/`：

- `source_report.json`：版本、snapshot ID、行数、导出 SHA-256、源端参考延迟。
- `source_queries.jsonl`：所有源端 SQL、query ID、结果行数及结果哈希；避免把 10 万行重复纳入仓库。
- `engine_seed42.json` / `engine_seed2026.json`：两轮正确性和性能结果。
- `materializations_seed*.json`：首次 lookup 前的完整状态观察。
- `environment.json`：代码/二进制/数据哈希、构建环境和原始文件路径。
- `rust_tests.log` / `python_tests.log`：单元测试结果。
- `quality_checks.json`：构建、测试、Clippy 和格式检查记录。

原始导出数据、完整查询结果日志和 ReadySet storage 保留在 `/tmp/readyset-databend-m1/`。
未执行任何 DROP，也未删除现有文件。

## 下一步

M1 已验证静态链路，可以进入 M2：

1. 将 M0 验证的 Stream 消费落入持久化 outbox 和 batch metadata。
2. 给 ReadySet 引入可比较的批次位点、提交与重放协议。
3. 对同一批数据验证 UPDATE / DELETE、重复投递和崩溃恢复。
4. 在持续写入压力下验证同步延迟及随机 key P99。
5. 单独接入 SQL 协议入口，测量真实应用端到端延迟。

M1 没有验证：服务端崩溃、源表 DDL、超大表容量、批量/范围查询、多租户权限、
同一时刻的源端强一致读取、多计算集群路由或长期生产负载。
