# 持续写入与高并发冷读（2026-11-16）

所有测试都在真实 Databend 上运行（`http://192.168.191.96:8000`，v1.2.962，单个 query 节点，对象存储是同机的 rustfs）。
只新建 `readyset_gateway_wrc_*` 库，全部保留。
压测器、Databend query、rustfs 和 readyset-databend 都在同一台 32 核机器上。

**测试拓扑和生产不同。** 这里写入、Stream 消费、转发的读都打到同一个 Databend 节点，进程也都在同一台机器上。
生产计划用 multi-cluster：写入在另一个集群，ReadySet 连接的集群后面有多个接入节点。
所以"读写同时"阶段测到的影响偏大，其中一部分是 Databend 节点和 CPU 的争抢，不是 ReadySet 本身造成的。

## 修复内容

批次里的只读元数据查询（提交前的 `DESCRIBE` 表结构检查、读 `system.streams` 的 Stream 版本），遇到瞬时错误时退避重试，最多 3 次（0.4 s、0.8 s、1.6 s）。
它们走自动提交的 admin 会话，不在 capture 事务里，重复执行没有副作用。

瞬时错误指的是和语句本身无关的失败：
- 传输错误（连接失败、连接被重置、超时）；
- HTTP 5xx 或 429；
- Databend 错误码 2001（内部连接错误，例如 query 节点到 meta 的 broken pipe）。

SQL 错误（语句错误、对象不存在、权限不足）和表结构变化不重试，立即失败。

修复的起因是 `wrc1`：一个批次读完 Stream、已经写了本地之后，`DESCRIBE` 收到一次 HTTP 500 / 2001，表失败，1,000 万行整表重建了 91.7 秒。
修复后的 `wrc2`、`wrc3` 里没有再因为 `DESCRIBE` 失败而重建。

新增单元测试：
- `only_statement_independent_upstream_failures_are_transient`：错误分类；
- `schema_check_retries_transient_admin_failure`：模拟 `DESCRIBE` 先返回一次 500 / 2001，第二次成功，表结构检查通过。

## 测试方法（`poc/write_read_contention_verify.py`）

- **数据：** 1,000 万行，字段 `id`、`ext_id`（`sha2(id)` 前 24 位，唯一，非 cluster key）、`cust_id`、`amount`、`payload`。
- **实例：** partial 模式，缓存内存 2 GiB，`max_staleness` 10 秒，缓存建在 `id` 和 `ext_id` 上。读用 `ext_id` 均匀随机点查，所以大多数读是冷读，要从本地持久化的 base 回填。
- **每档并发跑三个阶段，每段 40 秒：**
  1. 只读；
  2. 只写：每秒在 Databend 上 `INSERT` 1,000 行新行，`UPDATE` 100 行随机老行；每轮插入的最后一行用探针轮询，记录多久能在本地读到；
  3. 读写同时。
- **每阶段记录：** 读的 QPS、延迟、路由和错误；转发原因；每 0.2 秒采样的表状态；批次耗时；写入后在本地可见的时间；整机和各进程的 CPU（核数）。
- 阶段结束时还没看到结果的探针记为 `cut_by_phase_end`，不算"不可见"。

## 结果

三轮的 `report.json` 分别在 `wrc1/`、`wrc2/`、`wrc3/` 下。

| 轮次 | 程序 | 有效数据 | 说明 |
|---|---|---|---|
| `wrc1` | 修复前 | 并发 64 | c64 读写同时阶段结束后，`DESCRIBE` 失败导致整表重建 91.7 秒，c256 三个阶段全部受影响，作废 |
| `wrc2` | 修复后 | 并发 64 | c256 期间同机有其他人启动了 s3tests 和 curvine 压测，整机 CPU 97–98%，c256 作废 |
| `wrc3` | 修复后 | 并发 256 | 期间整机 1 分钟负载均值最低 8.5，中位数 13.7，最高 25.2 |

### 并发 64（`wrc2`）

| 指标 | 只读 / 只写 | 读写同时 |
|---|---|---|
| 读 QPS | 10,920 | 6,788（−38%） |
| 读 p50 / p99 / p99.9 | 5.95 / 10.2 / 24.3 ms | 6.9 / 29.3 / 801 ms |
| 读路由 | 100% 本地 | 99.77% 本地，630 次转发（`source_applying` 585，`stale` 118） |
| 读失败 | 0 | 0 |
| `INSERT` / `UPDATE` p50 | 75 ms / 3.47 s | 652 ms / 5.14 s |
| 批次耗时 p50 | 3.31 s | 4.43 s |
| 写入后在本地可见 p50 / 最大 | 5.10 / 7.63 s | 5.15 / 5.94 s |
| CPU（核） | readyset 7.78；只写时 Databend 9.89 | readyset 5.57，Databend 10.78，rustfs 2.40；整机 70% |

- **读没有拖慢写入：** 写入后在本地可见的时间基本不变。这段时间主要花在 Databend：`UPDATE` 本身要 3.5–5 s，带更新的批次读 Stream 约 3 s。
- **写对读的影响：** 一是批次持有 gate 期间（包括读 Stream 的那几秒）读被转发，每次约 0.8 s，按 630 次 × 约 0.8 s 估算，闭环压测下这部分等待约占 64 个 worker 总时间（64 × 40 s）的 20%；二是同机 CPU 争抢。

`wrc1` 的并发 64 结果基本一样：只读 10,699 QPS；读写同时 6,931 QPS，转发 533 次。

### 并发 256（`wrc3`）

| 阶段 | 结果 |
|---|---|
| 只读 | 15,218 QPS，p50 17.0 ms，p99 25.5 ms，p99.9 58.8 ms，100% 本地；readyset 9.29 核，整机 44% |
| 只写 | 批次 p50 3.39 s；写入后在本地可见 p50 5.11 s，最大 7.58 s；45 次 `source_applying` 转发 |
| 读写同时 | 2,210 QPS，p99 3.56 s；**2,464 次读失败**（Databend 返回 HTTP 500 或 2001）；表失败一次，整表重建 62.3 秒；写入后在本地可见 p50 14.8 s |

读写同时阶段的过程：
1. 批次变长，表 `stale` 以后，256 个并发的读全部转发到唯一的 Databend 节点。这个节点同时还在执行 `UPDATE`。
2. Databend 内部的一条 gRPC 连接被对端断开（单节点部署，应是到 meta 的连接）（`GoAway too_many_data_frames ENHANCE_YOUR_CALM`）。被转发的读收到 500 / 2001，原样返回给了客户端。
3. 同一时间，批次的 ROLLBACK 也失败了（`rollback also failed`）。ROLLBACK 走 capture 事务，不在本轮的重试范围内。表失败，本地已经写了半批，于是整表重建。

这里压垮的是单个 Databend 节点：它同时承担写入、Stream 计算和全部转发读。在生产拓扑下（写入在另一个集群，读集群有多个接入节点），这个场景的触发条件大部分不存在。

## 正确性

- **`wrc1`、`wrc2` 结束时：** 本地行数和 Databend 一致（10,039,000、10,033,000）；各抽 40 个键（20 个老行，20 个新行），全部本地返回，值和 Databend 一致。
- **`wrc3` 结束时：** 表还在失败状态，本地 10,016,000 行，Databend 10,018,000 行，抽样全部转发。
- **`wrc3` 用同一个持久化目录重启后：** 9.0 秒续接（`resumed`），本地行数 10,018,000，和 Databend 一致；抽 60 个键（30 个老行，30 个新行），全部本地返回，值全部一致。

三轮里没有出现错误数据。失败时都是转发或报错，不会返回旧数据或错误数据。

## 没有做的改动

以下改动按生产拓扑（multi-cluster，写入在别的集群，读集群有多个接入节点）决定暂不做：
- 批次先读完 Stream 再写本地。做了可以缩短 gate 持有时间，COMMIT 前出错也不用整表重建。
- 限制同时转发到 Databend 的读的数量。
- 有上限地放宽新鲜度，旧了但没超过上限时继续本地返回。

## 未覆盖

- 写入在另一个集群、读集群有多个接入节点的拓扑，本轮没有测。
- 经过负载均衡访问多个接入节点时，capture 事务依靠 `X-DATABEND-STICKY-NODE` 固定在同一个节点上。这一点只在单节点上跑过。
