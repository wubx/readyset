## 缺陷

本服务自己发给 Databend 的请求（首次加载、同步、表结构检查、读 Stream 版本、确认语句是否结束），用的都是 `src/upstream.rs` 的客户端。这个客户端只在会话 `need_sticky=true`（事务进行中）时才带 sticky 头。
可是几乎每条语句完成后都会再发一次 `/final`，所以自动提交下的语句都可能 404，包括 COMMIT 之后的那次 `/final`。

**修复前的复现（`mn_old_w100/`）：** 表连首次加载都完不成。
- 每次加载都在 `DESCRIBE` 的 `/final` 上收到 404；7 次自动重试（`table_recovery_failed`，attempt 1–7）全部失败，退避间隔涨到 300 秒，本地 0 行，所有读都转发。
- 这一轮已经无法继续，用 SIGINT 结束。按代码分析，即使加载碰巧成功，之后每个批次的 COMMIT（它的 `/final` 不带头）和 `DESCRIBE` 也会被判为失败，触发整表重建。

## 修复

一条查询的所有后续请求（分页、`/final`、`/kill`）都带上这条查询最近一次响应里的 `node_id`，不管会话是不是 sticky。新语句仍然只在会话需要时（事务或临时表）才固定节点。

新增单元测试（用模拟上游）：
- `continuations_are_pinned_to_the_query_node_in_autocommit_too`：自动提交下，单页结果、多页结果和流式读取的每个分页和 `/final` 都带节点；新语句不带。
- `statements_in_a_transaction_are_pinned`：事务中的语句带节点。

测试脚本里自己的 HTTP 客户端，也按同样的规则补上了 sticky 头；没补之前，测试工具本身在多节点下就会 404。

## 修复后的结果（都经过 8022）

### JDBC 兼容性、会话和读写混用

每一轮都是 64 个读线程。写入那几轮外加 1 个写线程，在同一地址上插入、更新，并且每次都立刻读回。

| 轮次 | 写入 | 用例 | 读 QPS | 读 p50 / p99 | 负载阶段本地比例 | 读己之写 | 最终一致性 |
|---|---|---|---|---|---|---|---|
| `mn_new_w0` | 无 | 22/22 | 5,436 | 10.2 / 42.0 ms | 99.68% | — | 行数一致，11 个抽样键一致 |
| `mn_new_w100` | 每 100 ms | 22/22 | 1,887 | 20.0 / 576.9 ms | 98.05% | 54 次全部通过 | 行数一致，38 个抽样键一致 |
| `mn2_mn` | 每 100 ms | 22/22 | 5,188 | 10.2 / 203.7 ms | 98.73% | 118 次全部通过 | 行数一致，45 个抽样键一致 |
| `mn2_single`（单节点 8000，对照） | 每 100 ms | 22/22 | 5,485 | 10.1 / 132.1 ms | 98.38% | 212 次全部通过 | 行数一致，45 个抽样键一致 |
| `mn2_mn2` | 每 100 ms | 22/22 | 5,202 | 10.2 / 106.3 ms | 98.69% | 116 次全部通过 | 行数一致，45 个抽样键一致 |

- **会话隔离：** 每轮都通过。连接 A 写入后立刻读，经 Databend 读到了；连接 B 同时在本地读，还看不到 A 的写入，符合预期。
- **事务、临时表和批量插入：** 每轮都通过。显式 `BEGIN` 的提交和回滚，事务内的读转发，同名临时表只在本会话可见，`executeBatch` 走 presign 上传。
- **表失败：** 五轮都没有出现，事件只有首次加载的 `table_recovered`。
- **最终一致性的检查方法：** 写入结束后，等表追上，再比较本地行数和 Databend 的 `count(*)`；再抽查 5 个老键和最多 40 个新写入的键，经本服务读取并和 Databend 逐行比较。这几个键全部是本地返回的。
- **`mn_new_w100` 的 QPS 偏低：** 只有 1,887 QPS、写线程每轮 1.1 秒，那段时间同机有其他人启动了 s3tests（pytest），占满了多个核。之后在同样条件下交替跑了"双节点、单节点、双节点"三轮（`mn2_*`）：双节点 5,188 / 5,202 QPS，单节点 5,485 QPS，差 5%。
- **写线程变慢：** 双节点下写线程每轮约 510 ms，单节点约 284 ms。每条写入的启动和 `/final` 都要经过 Python 实现的代理，还可能被转发到另一个节点，这是测试代理带来的额外开销，不是本服务造成的。

## 未覆盖

- **按连接分配的负载均衡：** 只测了每个请求轮询，这是最严格的情况。按连接分配的负载均衡会让多数请求自然落到同一节点，更宽松。
- **节点宕机：** 没有测节点重启或下线。事务和读 Stream 都绑定在一个节点上，那个节点重启时，进行中的批次会失败（`SessionLost`）。如果本地已经写了这批的一部分，按现有规则要整表重建。
- **其他客户端：** 只测了 databend-jdbc 0.4.8；bendsql 和 Python driver 在多节点下的行为没测。
